# The platform is the operator's agent VPS, and what it absorbs from claude-tmux

ADR 0006 deprecated claude-tmux and ADR 0007 decided the session model beneath it, which left open what this repo _is_ once the operator's environment ports into it, and which of claude-tmux's capabilities come along. Answering that one convenient feature at a time is how "most of it" arrives without anyone deciding to, so it was answered as a written list (issue #72). **This repo is an agent VPS set up with one command**: a Target that runs unattended Runs, hosts attended Sessions, and gives the operator's own devices secure access to its services. The Run-only posture stays the default install. Two toggles, both off by default and both reported by `status`: **sessions** — the per-Project session containers, the Docker socket exposure and the claude-mem service, which travel together because memory without Sessions has nothing to record — and **access** — the VPN of ADR 0011, independent because a Run-only Target with its dashboard reachable from a phone is a real configuration. One npm package carries everything; session code is not excluded from a Run-only install, because the trust boundary is the socket exposure ADR 0007 already gates per Target, and excluding code protects nothing extra.

**Ported.** Session launch and attach; per-Project session containers created idempotently; a seeded tmux config; the operator's git and `gh` setup signing with the agent's key; the skill set already in `extras.Dockerfile`, joined there by tmux, an editor and bash; Docker socket exposure to Sessions; WireGuard with its DNAT allowlist and the Cloudflare DDNS updater, as CLI-managed capabilities (ADR 0011); and shell history, which claude-tmux never persisted.

**Retired, each with the reason that keeps it from returning by convenience.** `setup-vps.sh` — the creator CLI replaced it. The multi-language toolchain image — contradicts ADR 0003. GSD — retired outright; nothing here may mention it. The Mac-side dashboard — dead, its attach script does not exist. `projects.yaml` and the per-project codegen — ADR 0007 derives Sessions from the Project list and generates its own files. The claude-mem CORS `perl -pi` patch — it never took effect, the minified callback is named differently in the pinned build, and patching minified vendor code is not a design. The `claude` launcher wrapper — nothing is scrubbed here, since a Session needs the same GitHub token and identity as a Sandbox for the one-identity rule to hold, and how the operator invokes Claude Code is their own config. The statusline and MCP wiring as platform features — they are the operator's Claude Code config, persisted and never shipped: anything the package writes into `~/.claude` is something it must then keep working across Claude Code releases, and the statusline fetched by SHA is what that maintenance looks like. zsh and oh-my-zsh — the Session shell is bash, because the agent writes bash by default and a zsh login shell turns that into a rewrite after every first error. The `~/.agents`, `~/.config`, `~/.local/share`, `~/.npm` and `~/.codex` volumes — `~/.agents` is where the image installs skills and a volume over it would hide them; the rest are caches, a binary the image now carries, and another agent entirely. `ANTHROPIC_API_KEY` in any container — the API billing path agents never use; it is not set in the first place.

**Ported differently: claude-mem is one worker service on the Target**, resolving ADR 0007's deferral. The plugin's single host setting is both where the worker binds and where hooks connect, and every hook's auto-start checks health on 127.0.0.1 only and spawns a local daemon when nothing answers, so pointing the plugin at a remote worker does not work and one worker per session container means N writers on one SQLite file. Instead: the worker container mounts the shared `~/.claude` volume and runs the _installed plugin's own_ worker script, so plugin and worker cannot drift and a plugin update is a worker restart; every session container runs a loopback forwarder to it, so the unmodified plugin on default settings sees a healthy local worker and never spawns one, and the worker's localhost-only admin routes refuse restarts from Sessions, which is right for a shared service. The worker's origin check accepts only localhost and cannot be configured, so a small reverse proxy in the service rewrites the Origin header — **temporary by declaration**, removed when an upstream change adds a configurable origin list. The worker summarises with the `claude` CLI, so it gets the Run token. Its data directory is configurable, so the VPS keeps its existing store. Runs do not write to it: the Run Log is a Run's memory (ADR 0009).

**Credentials: attended surfaces log in, unattended surfaces get the minted token.** A Session authenticates Claude Code with `claude auth login`, persisted in the shared `~/.claude` volume: it refreshes itself, so an agent left in a detached Session does not go dark when a static token expires; it carries MCP OAuth state; one login per Target serves every Project. A session container therefore must not carry `CLAUDE_CODE_OAUTH_TOKEN`, or the login is silently ignored — ADR 0007's "same credentials as a Sandbox" narrows to the GitHub token, author identity and signing key. The Run token is present under a non-magic name so a Sandbox started from a Session receives it as `CLAUDE_CODE_OAUTH_TOKEN`; Runs and the claude-mem worker use the token, because an OAuth flow has nowhere to happen unattended, and mounting the login into a Sandbox would put operator state into an unattended container, which ADR 0006 keeps out. The cost, stated: two places a Claude credential lives on a Workstation Target, both the same subscription. This reverses claude-tmux, which had no token and an interactive login only.

**The platform persists the operator's config and stays out of it.** It persists `~/.claude` and a session-state volume holding bash history and, if present, the operator's `.bashrc` and `.tmux.conf`, sourced by the image's startup files; it seeds a tmux config once and writes nothing else. First-time setup on a fresh Target is a README checklist of `claude` commands, not a seed command.

## Considered Options

- **A harness that dispatches Runs, with Sessions as a footnote** — rejected: it undersells the thing the operator lives in daily, and the two-posture design of ADR 0007 already committed the repo to more.
- **Two products in one repo, or a second package for session features** — rejected: a release process doubled for one operator, and a CLI on the dev machine that diverges from what the Target can do.
- **Session code excluded from a Run-only install** — rejected: a Run-only Target has no session containers to exploit, so exclusion protects nothing the socket gate does not.
- **Injecting the Run token into Sessions, one credential on the Target** — rejected: a static token expires and cannot refresh, and it carries no MCP logins. A login is the canonical attended flow and the one claude-tmux proved works headless.
- **One claude-mem worker per session container** — rejected: N writers on one SQLite file over a bind mount, the contention ADR 0007 deferred, and N places for the UI to be.
- **Patching the plugin's auto-start to honour a remote host** — rejected: the maintenance the CORS patch already demonstrated; the loopback forwarder needs no change to the plugin.
- **The package shipping the operator's Claude Code config as it stands** — rejected: see the statusline; every such file is a compatibility promise against Claude Code releases.
- **A CLI migration step off claude-tmux** — rejected: there is one instance to migrate, and the only thing worth preserving is the memory store, which the data-directory setting already covers. The cutover is manual and documented in the issue that retires claude-tmux.

## Consequences

- The README's opening sentence describes an agent VPS, not a harness. The Run-only default is stated as the default, not the product.
- One platform-owned external network, created by the install, is joined by the stack, the claude-mem service and every session container, which keep their separate compose projects. It gives Sessions name resolution to the Harness and the worker without host networking, which would be a bigger hole than a shared network.
- A Session gets the same GitHub token and author identity as a Sandbox, nothing scrubbed; `COMPOSE_PROJECT_NAME` is simply never set inside a session container, and the isolation claude-tmux bought by unsetting it is structural here, per ADR 0007.
- `CONTEXT.md` gains Memory, Access, Peer and Exposed Service, and corrects two terms: a Session is the per-Project container and its tmux server, never a window; a Workstation Target holds the operator's Claude login and exposes the Docker socket, and both are why it must be trusted.
- ADR 0007's credentials clause is narrowed, and its claude-mem deferral resolved, by this decision. ADR 0006's loopback clause is qualified by ADR 0011.
- claude-tmux's zsh history is not migrated. The Session shell is bash, and it was a few kilobytes in the wrong format.
- #9's fog on the operator tier closes. #66's build issues are sliced under #72.
