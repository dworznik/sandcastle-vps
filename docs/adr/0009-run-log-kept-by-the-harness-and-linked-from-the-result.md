# The Run Log is kept by the Harness under the Project, keyed by the Dispatch, and linked from the result

Opening a Run's log from the Orchestrator's run page is the first thing an operator reaches for when a Run goes wrong, and it was not possible. The Harness logged to a file sink under `.sandcastle/logs/<task-branch>.log`, which a re-dispatch to the same Task Branch — the documented way to iterate — overwrote; the captured Claude Code transcript landed under the Harness container's home, which is not a volume; and the result carried a path the operator had to go and find over SSH.

What the Orchestrator keeps decides the shape of the fix. It persists the Dispatch, the Run's status and timings, and the function's return value or error — durably. It does **not** ingest application log output: the SDK's logger has no transport to the server, and there is no log sink to point a stream at. A Run's log will never arrive in the Orchestrator by logging harder at it. **It is kept by the Harness and linked from the result**, which is the one hook the Orchestrator's run page offers, and it is enough.

**A directory per Run, under the Project.** `<project>/.sandcastle/runs/<id>/`, created as soon as the Project is resolved and before anything that can fail, so a Run that dies in its first second still has a place that says so. It holds the reduced events (`events.jsonl`), Claude Code's `stream-json` verbatim (`stream.jsonl`), the Sandbox's own hook lines (`hooks.jsonl`), sandcastle's rendered log (`sandcastle.log`), and the captured session transcript with its subagents (`session/`). Under the Project because that is the disk both the Harness and the Target see at path parity, and because the Orchestrator's store is the other thing on the Target that nothing prunes (ADR 0005); retention is one follow-up for both.

**Keyed by the Dispatch's id, not the function's run id.** The brief asked for the run id. The ids a Dispatch answers with are the Orchestrator's _event_ ids; the function's run id is assigned when the Orchestrator starts the function and is unknowable at Dispatch time without a round trip to its API. Keying on the event id is what lets the Dispatch answer carry the link and `sandcastle-run` print it, so the live tail is one click away before the Run starts. One Dispatch is one Run while retries stay at zero (ADR 0002); the run id is recorded inside, and the one way two Runs share an event — a rerun from the dashboard — gets a directory with the run id appended. The run page is served for any well-formed id, started or not, and tails `events.jsonl` itself; the files are served only once they exist.

**Observation from both sides of the Sandbox wall.** The Harness reduces the raw stream into one event per model call, subagent lifecycle, invocation result and rate-limit window, with the subagent semantics the proof of concept established: subagents run in the background and re-invoke the parent, a child's blocks interleave with the parent's, open calls are closed per thread. Inside the Sandbox, user-scope Claude Code hooks append one reduced line per event to the hooks file — reduced in the hook, since a `Write` tool's input is the whole file. **Only that file is mounted, not the run directory**, so the agent appends its own account and cannot touch the Harness's records beside it. The two sources join on ids the stream and the hooks share.

**Served on the existing loopback surface.** `GET /runs/<id>` is the page and `GET /runs/<id>/<file>` the files, published on Target loopback like the Dispatch surface, so the tunnel the operator already opens is the access path and nothing new authenticates. The URL is built from the Harness's own port; through a tunnel mapping the same port it works unchanged.

## Considered Options

- **Sending the events to the Orchestrator as Inngest events** — the lines are the right shape for it, but the event names would be a contract other functions trigger on, and that deserves its own pass. Separate issue; this keeps the file.
- **Step boundaries, to put phase timings on the Orchestrator's run page** — the replay hazard ADR 0008 documents. Own ticket.
- **Keying the directory by the function's run id** — what the brief said; rejected because the Dispatch cannot know it, so the link could only be handed out after the Run started. A lookup from the event id through the Orchestrator's API was the alternative, and adds a race and an API dependency to a keyless route for a mapping that is already 1:1.
- **An index from event id to run directory** — one more thing to keep consistent, for a scan over tens of Projects.
- **Mounting the whole run directory into the Sandbox** — what the proof of concept did; rejected because it hands the agent write access to the Harness's own records.
- **A `.claude/` in the worktree for the hooks** — rejected: observation would land in the Project and depend on workspace trust.

## Consequences

- Every Run writes a run directory; nothing prunes them, as nothing prunes the Orchestrator's store. Same follow-up as ADR 0005.
- The Run result carries `logs: { url, dir }` and a capped `tail` of the last events that says when it was cut; a failed Run's error message carries the URL; the pull request body carries it in place of the transcript path ADR 0008 put there. `logFilePath` is gone from the result — `sandcastle.log` is in the directory.
- Onboarding adds `runs/` to the `.sandcastle/.gitignore` that `sandcastle init` writes. A Project Onboarded before this needs that line added by hand, or its shared checkout shows the directories as untracked.
- The `rate_limit` event is the input the Limit Gate will read. It is surfaced here and gated on nowhere.
- ADR 0002 is untouched: a Run is one opaque unit with retries disabled, and its log is a file the Harness keeps rather than durability the Orchestrator provides.
- No token reaches a hook command line, the hook file or the served files: the hook command reads nothing from the environment, tool inputs are truncated in both the hook and the reducer, and the two files that carry tool output whole — the raw stream and the transcript — are scrubbed of the Harness's credential values as they are written, as is every file as it is served. The scrub is an exact-string replacement of the two tokens; it does not find a secret the agent has transformed.
