# Interactive sessions as per-Project containers with forwarded authority

ADR 0006 said interactive sessions become sandboxes — sandcastle's `interactive()` on a worktree — and left the detail as fog. Building on that reveals it cannot work: `interactive()` is a local child process inheriting the caller's stdio, `docker exec`ing into a container it removes when that process closes, with no way to re-attach and no notion of resuming a session by name. An SSH drop destroys the session and its container. It also has to run where the checkout, the Docker daemon, git and node all are, so it cannot be driven across a Connector — and `docs/connectors.md` forbids the terminal multiplexing an attach would need. **A Session is therefore not a Sandbox.** It is a long-lived, per-Project container in which sessions are tmux windows; tmux owns the pty, which is the one property sandcastle does not provide and is unlikely to. A Session may still _start_ a Sandbox — a tmux window running `interactive()` survives a dropped connection because tmux holds its terminal — so the two compose rather than compete.

**One session container per Project, built from that Project's own image.** The alternative, one container per Target with a shared image, is what the deprecated claude-tmux does, and its 248-line Dockerfile carrying Go, Flutter, uv, wrangler and sentry-cli is the reason not to: every Project's toolchain accumulates in one place, and two Projects wanting different Node versions is unresolvable. Deriving from the Project's image applies ADR 0003 consistently — a Project owns its image — so dependencies stay declared in the Project's own `.sandcastle/Dockerfile`, maintained by whoever already maintains them. tmux and an editor are added to `docker/sandbox/extras.Dockerfile`, so one image per Project serves both Sandboxes and Sessions. The workspace root is mounted at path parity in every session container, so work spanning repos still works from any of them; only the toolchain is Project-scoped.

**The operator's signing key is forwarded, never resident.** A session hosts operator work — the reason claude-tmux exists — which needs the operator's identity, not the agent's. The tempting move was to place a signing subkey on the Target behind a passphrase, since the operator's unprotected primary key is already in the claude-tmux container and ADR 0006's _"the VPS holds only agent credentials"_ is therefore already untrue in practice. The better answer is `ssh -A`: `ssh-keygen -Y sign` signs from a forwarded agent with no private key on the remote at all, which was verified end to end before this was decided. So the rule is restored rather than rewritten — a Target holds only agent credentials, and signing capability arrives with a connection and leaves with it. The cost is that a forwarded socket goes missing in three silent ways: a stale tmux environment, `docker exec` not carrying it, and an ssh multiplexed master established without forwarding, which beats a later `-A`. All three surface only as an unsigned commit, so all three become preflight checks.

The deciding trade-off: forwarded authority needs plumbing that can fail quietly, while a resident key needs a rotation discipline that does not exist. Neither is simply safe — forwarding keeps key _material_ off the Target, but anything that can reach the live socket can ask it to sign, which is why the trust rule in the consequences below belongs to this decision rather than being a caveat on it. What settles it is that forwarding's exposure is bounded by the length of a session while a resident key's is permanent: a Target compromised with nobody attached yields nothing.

## Considered Options

- **Sessions as Sandboxes, per ADR 0006** — rejected on evidence: `interactive()` cannot survive an SSH drop, and its container is removed on exit.
- **One session container per Target with a superset toolchain image** — rejected: claude-tmux's own Dockerfile is the argument against it, and it contradicts ADR 0003.
- **A signing subkey at rest on the Target, with a passphrase** — rejected once forwarding was shown to work; see the trade-off above.
- **Agent identity for session commits** — rejected: a session that cannot sign its own ADR commit is a session whose work finishes on the dev machine, so it would not be used twice.
- **Plain `docker run` for session containers** — rejected: the Dev Containers spec sources a container from an image, a Dockerfile or a compose service, with no repo-level way to describe an already-running one, so this silently costs the editor-attach workflow.
- **Session services in the platform's own compose project, behind a profile** — rejected: whether `--remove-orphans` spares inactive profiles is a compose semantic that has shifted between versions, and the failure it would cause is deleting a live session during an upgrade.

## Consequences

- **ADR 0006's session clause is superseded, not amended.** ADR 0001's rationale amendment is corrected too: a Session works in the Project checkout directly, not a worktree, so the branch-strategy lock binds Runs and not the operator. An agent invoked _from_ a session still gets a Task Branch, because sandcastle creates the worktree.
- **Sessions are opt-in per Target**, so the default install still produces a Target holding only agent credentials. Two postures exist and `status` reports which: a Run-only Target, and a Workstation Target with session containers and the Docker socket exposed to them.
- **A Project you open a session on is a Project you trust with your Target.** Its committed Dockerfile can plant shell startup files that run with the Docker socket available and a live forwarded agent. A Sandbox has neither, so Onboarding a repository you do not control is acceptable for Runs and is not acceptable for Sessions.
- Session containers run in a **separate compose project** per Project, so the install's `compose up -d --remove-orphans` cannot reach them. `status` finds them with `docker ps`, not `compose ps`.
- Onboarding generates two artifacts it did not before: a compose file in the install directory, and a gitignored `.devcontainer/devcontainer.json` in the Project — the only thing written into the repository, because the spec requires that path. The `.gitignore` line is deliberate: an untracked generated file in a repository an agent commits to is a latent accidental commit.
- The agent socket reaches the Target at a fixed path via `ssh -R`, not a symlink, which would dangle inside the container, nor a relay, which can die.
- One shared `~/.claude` volume serves every session container; path parity keeps each Project's memory namespace distinct. It must be an external volume, since the containers are in separate compose projects.
- **claude-mem is deferred.** A 235 MB SQLite database with a worker daemon on a port is a single-service question, not a mount, and belongs with the wider claude-tmux port rather than here.
- Operator commit signing moves from GPG to ssh format when sessions ship, so that one mechanism covers the agent and the operator. Until then GPG remains the rule.
